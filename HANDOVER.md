# Vogelvrij — project handover

Last reviewed against the local source tree: 2026-09-25. This describes what is implemented, not a deployed public website.

## Purpose and current state

Vogelvrij collects public aircraft-position observations around Brussels for later analysis of traffic over a region affected by a new flight route. The intended end product is a public information site with traffic statistics and visualizations. Aircraft position and altitude are **not noise measurements**. The current movement detector identifies plausible approach encounters from one observation; it does not establish that an aircraft landed. A simple local page now queries and polls movement counts and historical breakdowns, METAR wind, and a TAF wind forecast. Independent EBBR METAR and TAF one-shot collectors and a foreground continuous collection runner are available, but origin/destination enrichment, validated statistics, and a deployed public site remain to be built.

Today the project is a Python command-line collector with approach-movement detection, a local PostgreSQL/PostGIS database, aircraft and movement console reports, two generated Google Maps HTML pages, and a locally served read-only public-page prototype with movement statistics. The page is not deployed. It is separate from Lifefinance1 and does not include that project's React/FastAPI/Clerk/deployment stack.

## Architecture and source layout

```text
adsb.lol geographic API
    -> vogelvrij-collect (fetch, normalize, filter)
    -> PostgreSQL/PostGIS (collection runs + aircraft observations + approach movements)
    -> show-aircraft.sh (latest observation per aircraft across runs)
    -> show-movements.sh (all detected movements)
    -> vogelvrij-map (static HTML snapshot of the latest run)
    -> vogelvrij-map-history (static tracks across the ten newest runs)
    -> vogelvrij-web (read-only HTML page with current and historical movement counts and latest ten rows)
    -> local browser / Google Maps JavaScript API
aviationweather.gov EBBR METAR -> vogelvrij-collect-wind -> wind_observations
aviationweather.gov EBBR TAF -> vogelvrij-collect-taf -> taf_forecasts -> forecast timeline
```

## Collection and filtering behavior

The client calls `https://api.adsb.lol/v2/lat/{lat}/lon/{lon}/dist/{radius_nm}` with a 15-second timeout and User-Agent `BrusselsPlaneTracker/1.0`. Latitude/longitude and a radius greater than zero and no more than 250 nautical miles are required. `vogelvrij-collect` prints normalized aircraft with valid positions; this console output is **before** the database insertion filter, so its count can exceed the stored count. It does not print the full provider response.

Unless `--no-store` is specified, each successful call creates one `collection_runs` row, including calls with zero accepted aircraft. `store_collection()` evaluates each raw aircraft object. Current insertion rules in `repository._should_store_aircraft()` are:

1. Reject aircraft whose API `t` (ICAO type designator) is in `EXCLUDED_AIRCRAFT_TYPES` in `repository.py`. The collection currently contains only `C152` and `P28A`; matching ignores case and surrounding whitespace. Missing or other type codes remain eligible. This filters new observations only; it does not remove existing rows.
2. Reject `alt_baro` explicitly equal to `ground` (case-insensitive).
3. Use numeric `alt_baro`, falling back to numeric `alt_geom`; reject an unknown altitude or one above 10,000 feet. Exactly 10,000 feet passes.
4. Require numeric latitude and longitude.
5. Accept every remaining positioned aircraft regardless of approach polygon. This is the intended collection behavior: positions outside a corridor can appear in map/history views, while the downstream movement detector applies all four corridors and the heading/speed criteria to decide what counts as an approach encounter.

The observation time comes from the provider's top-level `now` timestamp when usable, otherwise from the local UTC clock. The run's `requested_at` is the database insertion time. Repeated sightings are deliberately separate observations; there is no uniqueness constraint or deduplication for observation ingestion. No descent/trajectory/airport-confirmation filter has been implemented to prove aircraft are arrivals.

### Movement detection

After `store_collection()` flushes a run and its filtered observations, `sync_movements_for_run()` examines those observations in the same database transaction. It accepts an observation only if it has a numeric position inside one of the four approach polygons, a numeric ground track within the requested inclusive ±10° range (25LR 240–260°, 07LR 60–80°, 01 0–20°, 19 180–200°), ground speed of at least 100 knots, and a nonblank ICAO aircraft address (`hex`). Missing speed, track, position, or ICAO address prevents movement creation. The first matching corridor in `APPROACH_AREAS` order is stored as `25LR`, `07LR`, `01`, or `19`; the directional checks normally disambiguate overlap. The observation's existing type, altitude and ground filters still run first. A `--no-store` collection creates neither observations nor movements.

For each ICAO address, the detector compares the newest movement's `created_at` to the current run's `requested_at`. A qualifying observation before 15 minutes have elapsed links to that movement and advances its last-observed time; it does not create a second row even if the callsign changed. At exactly 15 minutes or later, the next qualifying observation creates another row for the same aircraft. The first nonblank callsign is retained on an existing movement. Each linked qualifying observation also competes to supply the movement's stored `faf_altitude_ft`: the new altitude and `faf_distance_m` replace the old values only when that observation is strictly closer to the corridor's reference point. Barometric altitude is preferred, with geometric altitude as fallback. Equal or farther distances do not overwrite the prior height. This is a time-window heuristic, not flight-leg reconstruction: a continuously visible aircraft can create another movement after 15 minutes, and no landing is confirmed. There is currently no database constraint against two concurrent collector processes racing to insert a movement for the same aircraft; run one collector at a time until this is addressed.

At first insertion, each new movement snapshots the latest stored `aviationweather.gov EBBR METAR` observation by `observed_at DESC, id DESC`: reported wind direction in degrees, wind speed in knots, and `expected_approach` from the same gust-aware `predict_landing_approach()` rule as the live "Verwachte naderingsbaan" card. The detector reads that wind once per run only when a new movement is needed; later sightings never overwrite the snapshot. No METAR gives three NULLs, and no wind-feasible runway gives a NULL predicted approach. There is no age cutoff on the METAR and this remains a wind-only prognosis, not an observed or assigned landing runway. Existing movements are not backfilled because the METAR available at their original insertion may differ from today's data.

`faf.py` holds the comparison points and spherical distance calculation. User-supplied reference coordinates are 01/BR01F `50.795306, 4.453861` and 07LR/FD07L `50.879167, 4.309167`. The shared 25LR point is provisionally the arithmetic latitude/longitude midpoint `50.94140278, 4.65073611` of published B25LF and B25RF positions; it is not a published waypoint. The 19 comparison point `51.00306296, 4.53888170` is synthetic: from the [published 19 threshold and true runway bearing](https://ops.skeyes.be/html/belgocontrol_static/eaip/eAIP_Next/html/eAIP/EB-AD-2.EBBR-en-GB.html), it lies on the extended centreline at the same 5.707 NM threshold-to-reference distance as the supplied 01 point. It is not asserted to be a 19 FAF. The 25L/25R waypoint positions also come from that AIP. These comparison points select an observed height, not a measured altitude at the exact point or a certified approach altitude.

## Data model

| Table | Contents and status |
| --- | --- |
| `collection_runs` | One row per stored API response: request center/radius, request time, provider, selected response metadata (`msg`, `now`, `ctime`, `ptime`, `total`) and complete non-`ac` envelope metadata in JSONB. |
| `aircraft_observations` | One accepted aircraft state per run. It has an observation time, nullable normalized identity/position/altitude/speed/heading/navigation/signal/weather-like provider fields, and the full aircraft payload in required `raw_data` JSONB. The generated PostGIS `position` geography point and indexes support future spatial queries. A B-tree index on `collection_run_id` supports latest-run and recent-run map lookups. References its run; qualifying observations now link to a flight movement. |
| `flight_movements` | One detected approach encounter: creation time, aircraft ICAO address, first known callsign, approach corridor, first/last observation timestamps, nullable closest-reference-point altitude in feet plus its distance in metres, and nullable insertion-time METAR direction (degrees), speed (knots), and expected approach. Nullable origin/destination ICAO and IATA codes, provider, enrichment time, and route JSONB are reserved for future enrichment. Multiple movements can exist for the same aircraft on one day, separated by at least 15 minutes from their creation times. |
| `wind_observations` | Independent METAR observation time, direction in degrees, speed in metres/second, optional gust/source/raw JSONB. `vogelvrij-collect-wind` writes usable EBBR observations here. Provider-supplied `wd`/`ws` fields on an aircraft, when present, are stored separately on that aircraft observation; they are not the independent wind time series. |
| `taf_forecasts` | EBBR TAF bulletins keyed by station and exact raw TAF, with fetch/issue/validity times and full provider JSONB. They are forecasts, never measured wind observations. |

Most provider-derived aircraft columns are nullable because ADS-B fields vary by aircraft and message. Unknown or newly introduced API fields survive in `raw_data`, rather than requiring an immediate schema change. The SQL migration and SQLAlchemy model must be kept aligned when the schema changes.

## Local setup and daily operation

Prerequisites: Python 3.9+, Docker Engine/Desktop with Compose v2, and a Google Maps JavaScript API browser key only if generating the map. From the repository root:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
docker compose up -d db
vogelvrij-collect --lat 50.8503 --lon 4.3517 --radius-nm 25
./scripts/show-aircraft.sh
```

The example center/radius are request parameters, not the approach-polygon vertices. The DB defaults to `postgresql+psycopg://vogelvrij:vogelvrij@localhost:5433/vogelvrij`; set `DATABASE_URL` to override it. `POSTGRES_*` values in `.env.example` configure the local Compose database. Environment variables can be exported in the shell; the Python commands do **not** automatically load `.env`. `python -m vogelvrij` is another collector entry point. Use `--no-store` for a fetch-and-print-only call.

For a bounded sequence of collections, run `./scripts/collect-repeatedly.sh 60 10 --lat 50.8503 --lon 4.3517 --radius-nm 25`. The positional arguments are the interval in seconds (positive, decimals accepted) and the number of runs (positive integer); remaining arguments pass through to `vogelvrij-collect`. The first call is immediate, there is no sleep after the last, and a failed call stops the loop. The script uses the active environment's collector or the repository `.venv` fallback. It does not schedule itself, retry failures, or enforce provider rate limits; select a conservative interval.

For unbounded foreground collection under a service manager, run `./scripts/collect-forever.py`. It prefers this checkout's `.venv/bin` commands, otherwise installed commands on `PATH`. Flights default to `--lat 50.900167 --lon 4.460000 --radius-nm 15` every 60 seconds; `--flight-interval` (positive seconds) and the three location flags override these defaults. EBBR METAR and TAF run independently once each hour, starting immediately. The runner uses a monotonic schedule, skips missed slots, runs only one child at a time, logs failures and attempts the next scheduled run, and forwards shutdown to its active child on SIGTERM/SIGINT. Slow commands can delay due jobs; this is best-effort cadence without durable jobs, exponential backoff, or provider rate-limit enforcement. Run only one instance and avoid a concurrent aircraft collector against the same database because movement creation can race. A Linux systemd service example, including database environment configuration, is in `README.md`; this repo does not install or activate a service. The database must be available with migrations applied; repeated database failures do not end the runner.

For independent Brussels wind collection, run `vogelvrij-collect-wind` once per desired poll (or `vogelvrij-collect-wind --no-store` to print only). It calls `https://aviationweather.gov/api/data/metar?ids=EBBR&format=json` with a 15-second timeout and custom User-Agent. It selects the newest EBBR report by `obsTime`, displays `wdir` and `wspd` (knots), converts speed and optional gust from knots to metres/second for `wind_observations`, and preserves the report in `raw_data`. A matching source and observation time already in the table is not inserted again. HTTP 204, an empty report list, or missing/variable wind data inserts nothing. Direction 360° is stored as 0° to fit the existing database constraint. The command has no built-in loop, scheduler, or retry/backoff; schedule it separately from `vogelvrij-collect`, at a frequency mindful that most METARs update hourly and the provider rate-limits requests.

For the separate forecast, run `vogelvrij-collect-taf` once per desired poll (or `--no-store`). It calls `https://aviationweather.gov/api/data/taf?ids=EBBR&format=json`, selects the newest EBBR issue, prints its groups, and inserts a new `taf_forecasts` row only for a distinct raw bulletin. It does not update `wind_observations`, schedule itself, or retry failures. Migration 003 was applied to the current local database on 2026-09-19; other existing volumes need `docker compose exec -T db psql -v ON_ERROR_STOP=1 -U vogelvrij -d vogelvrij -f /docker-entrypoint-initdb.d/003_taf_forecasts.sql`. The migration is additive/idempotent and runs at init on a fresh volume. The first current EBBR TAF was stored in the local database as ID 1.

The initial SQL migration runs only on an empty Compose data volume. Editing it later will not migrate an existing database. Migration `002_flight_movement_detection.sql` adds `created_at`, `approach_corridor`, and an index; it was applied to the current local database on 2026-09-19. On any other existing database, apply it before running the updated collector with `docker compose exec -T db psql -v ON_ERROR_STOP=1 -U vogelvrij -d vogelvrij -f /docker-entrypoint-initdb.d/002_flight_movement_detection.sql` (adjust user/database if customized). The migration is idempotent and also runs automatically on a fresh Compose volume after 001. Do not erase the volume as a migration shortcut. `docker compose down` stops/removes containers while retaining the named data volume. `docker compose down -v` would remove that volume and should not be used casually.

For CD, use `docker-compose.test.yml` or `docker-compose.prod.yml` explicitly rather than editing `docker-compose.yml` on a server. The deployment files define the fixed Compose projects `vogelvrij-test` and `vogelvrij-prod`, use separate images and named volumes, and bind PostgreSQL only on `127.0.0.1:5434` and `127.0.0.1:5435`, respectively. On an existing volume, apply it with `docker compose exec -T db psql -v ON_ERROR_STOP=1 -U vogelvrij -d vogelvrij -f /docker-entrypoint-initdb.d/004_movement_faf_altitude.sql` (adjust credentials if customized), then run `python scripts/backfill-faf-altitudes.py` from the installed project environment to fill existing movements from their linked observations. ### Console and map views

`./scripts/show-aircraft.sh` chooses the latest observation for each nonblank `hex` across **all** stored runs and shows flight number, barometric height, true track in degrees, and latest observation time in UTC. Rows without a usable identifier remain distinct. This is a view-level deduplication, not a database merge.

`./scripts/show-movements.sh` shows **all** movement rows, newest detection first, with movement ID, callsign, aircraft address, approach corridor, insertion-time METAR wind and expected approach, detection time, and first/last observation times in UTC. The current database had no movements before this feature was installed; the detector does not backfill historical observations or wind snapshots.

For the latest-run map, set a restricted `GOOGLE_MAPS_API_KEY` in the environment and run:

```sh
vogelvrij-map
python3 -m http.server 8765 --directory generated
```

Then open `http://localhost:8765/planes_map.html`. The generator selects the newest run by database ID, includes only that run's stored observations with positions, and writes `generated/planes_map.html` by default (or use `--output`). It shows aircraft markers/list, all four approach polygons (25LR blue, 7LR green, 01 amber, 19 purple), and the **latest run's** search center and radius circle. The Dutch aircraft list orders observations by sighting time descending (ID breaks ties) and shows the sighting time in Belgian local time. An empty latest run displays no aircraft rather than falling back to an older run. Regenerate the file after each collection or a map-code change; the page does not update itself and is not a live website.

For a multi-run overview, run `vogelvrij-map-history` and open `http://localhost:8765/planes_history_map.html` with the same local HTTP server. The command selects the ten newest `collection_runs` by ID (or fewer if fewer exist), then their stored observations with positions. It groups observations by normalized ICAO `hex`; unknown identifiers remain separate. Within each aircraft, positions are ordered by observation time and ID, and consecutive identical coordinates are collapsed while keeping the latest observation details. The Dutch aircraft list orders aircraft by their last sighting descending and shows that time in Belgian local time. The map draws a line joining successive distinct positions, small colored dots at earlier positions, and exactly one red directional arrow at the final position per aircraft, alongside all four approach polygons. Lines interpolate between samples; they are not measured continuous flight paths. The history page does not show a radius circle because different runs may have different search areas. It is a static snapshot and must be regenerated after new collections.

The generated HTML pages embed the Google Maps key and stored aircraft details, are Git-ignored, and are written with user-only filesystem permissions. A browser key is visible to anyone who can load a page; restrict it to the Maps JavaScript API and allowed website referrers, and do not treat the HTML as a secret-preserving backend. Keep real keys out of source, commits, handover text, screenshots, and logs. For any public site, review the adsb.lol data attribution/ODbL obligations and the Google Maps key/domain setup.

For the public-page prototype, set a restricted `GOOGLE_MAPS_API_KEY`, run `vogelvrij-web`, and visit `http://127.0.0.1:8766/`. Optional `--host` and `--port` arguments change the bind address and port; `DATABASE_URL` controls the database. It queries on each page request and sends HTTP 503 if the database cannot be read. The HTML preserves the reference page's text and arrangement and hotlinks its banner and three icons from `bruegelvogelvrij.be`; it adds a statistics section above the footer with a half-width 07LR card, a matching wind card, 25LR/01/19 cards, and the ten latest movement rows. The wind card selects the newest `aviationweather.gov EBBR METAR` row by observation time and ID, shows exact reported `wdir` and `wspd` (degrees and knots) from retained raw data, an arrow pointing where the wind blows (180° opposite the METAR origin direction), and the observation time in Belgian local time. It also shows an expected landing approach based on that measured wind, using the same gust-aware runway-selection heuristic as the TAF cards; this is a wind-only prognosis, not the approach aircraft are observed actually using. With no wind row it shows an empty state; on narrow screens the two cards stack. Counts select `flight_movements.created_at` in the current Europe/Brussels day with a half-open interval, including DST changes. Recent rows order by `created_at DESC, id DESC` across all dates. Timestamps render in Belgian local time, nullable values as a dash, and text is escaped. A same-origin `/api/movements` JSON route returns only display fields (including latest wind and its prognosis) plus the newest collection-run ID, with no raw provider payloads; the external JavaScript polls it every 30 seconds while the page is visible and once on tab return. Polling handles Belgian midnight rollover and picks up new wind observations without a page reload. A failed poll retains the last values and displays a warning; the initial HTML is server-rendered so it still works without JavaScript.

Each of the four movement cards also shows estimated headwind/tailwind and crosswind in knots from that same METAR, with an unavailable state when no reading exists. The signed along-runway component is `speed × cos(|wind direction − heading|)` (negative means tailwind); crosswind is the magnitude of `speed × sin(|wind direction − heading|)`. The shared 07LR/25LR corridor cards use nominal magnetic headings 070°/250°, and 01/19 use 010°/190°. No magnetic variation correction is applied to the METAR's true direction. The figures are rounded to one decimal, labelled as estimates on the page, and are not operational runway wind data. Both initial HTML and the 30-second JSON poll derive them server-side.

A small light beside each component is red if its **unrounded** tailwind is at least 7 kt for 25LR or **greater than** 3 kt for 07LR/01/19, or unsigned crosswind is at least 20 kt on any corridor. Exactly 3 kt tailwind is allowed on the alternatives, matching the AIP's explicit inclusive note. It is green otherwise and neutral grey when no usable wind row exists. The API returns component text, light status, and corridor-specific accessible label; the initial HTML and 30-second update use the same server-derived thresholds. These display thresholds are not a safety clearance. The latest stored METAR can become stale; the wind card shows its observation time, but no automatic age cutoff is implemented.

The full-width forecast panel below the movement cards selects the newest currently valid stored EBBR TAF by issue time and ID. If none is currently valid, it selects the newest stored bulletin even if it is not yet valid or has expired. It labels the selection "Actueel", "Nog niet geldig", or "Verlopen" and continues to show its wind periods; only no stored/renderable bulletin yields an unavailable state. Validity uses a half-open interval (`valid_from <= now < valid_to`). Period arrows point **toward** the wind's travel direction while text reports the source direction, speed and optional gust in knots. Issue, validity and group times use Europe/Brussels. A `BECMG` wind group renders as a hatched transition from `timeFrom` to `timeBec`, followed by the prevailing wind through `timeTo`; this does not claim an instantaneous switch. `TEMPO`/probability groups without explicit wind are omitted rather than misread as calm. Explicit temporary wind is shown separately but does not replace prevailing wind. Only compact display fields reach `/api/movements`, so the raw TAF is not exposed. The panel updates on the existing 30-second poll, including a validity-status change while the same bulletin remains selected, and stacks on mobile. Forecasts do not affect the METAR-derived components or status lights. This simplified visualization does not interpret all TAF weather/cloud groups or provide operational guidance.

Each forecast card now also shows a wind-only landing-approach prognosis. `runway_prediction.py` compares TAF true wind direction with the individual true runway bearings in [Belgian AIP EBBR AD 2.12/2.20](https://ops.skeyes.be/html/belgocontrol_static/eaip/eAIP_Next/html/eAIP/EB-AD-2.EBBR-en-GB.html): 25L 249.89°, 25R 245.35°, 19 194.43°, 07R 69.89°, 07L 65.35°, and 01 14.43°. Gust speed replaces mean speed for conservative component checks when available. If either 25 end has tailwind <7 kt and crosswind <20 kt, `25LR` wins. Otherwise, candidates 19/07LR/01 require tailwind ≤3 kt and crosswind <20 kt; the feasible end closest in circular angle to the wind origin wins, with deterministic group-name tie-breaking. No feasible runway or unusable wind yields “Geen betrouwbare voorspelling.” A `BECMG` card reports the possible previous→new approach (or the same approach) during its transition window, without asserting a switch instant. A temporary wind group receives its own prognosis without changing the prevailing one. These are project heuristics: real runway assignment also depends on ATC, time-of-day preferential scheme, runway availability, visibility, safety and other factors. The measured-wind lights still use their older nominal magnetic headings without variation correction and are independent of this TAF prognosis.

If no key is set or there are no runs, the frame returns an explanatory 503 state. The map's ten runs are not necessarily the ten movement rows shown above it. The main page CSP allows `frame-src 'self'`; the map response has its own per-response nonce-based Google-compatible CSP and `frame-ancestors 'self'`. The Maps browser key is embedded in the map response and therefore visible to page viewers; restrict it to Maps JavaScript API and authorized HTTP(S) referrers. Counts are detector-created approach encounters, not confirmed landings; no database-driven push mechanism exists. Source attribution and limitations appear on the page. The server defaults to loopback, has no deployment/proxy/TLS setup, and must not be presented as a validated public traffic tally while the geometry and detection gaps remain.

To transfer all data, run `python scripts/export-database.py backups/<new-name>` against the source database. The output has one headered CSV per public application table plus a JSON manifest with columns, row counts, and SHA-256 hashes. The export uses one repeatable-read snapshot, skips PostGIS extension-owned tables and generated columns, and refuses to overwrite an existing destination. The directory has user-only access and `backups/` is Git-ignored, but copies elsewhere need equivalent protection because raw provider payloads are present. The CSV files do not include schema or extensions.

Create a separate empty PostgreSQL/PostGIS database with all migrations applied, then set its `DATABASE_URL` and run `python scripts/import-database.py backups/<new-name>`. The importer checks hashes and exact application table/column compatibility, locks and checks that every target table is empty, loads rows in foreign-key order, checks counts, and adjusts serial/identity sequences. It does not truncate. An import error rolls back row changes. See `README.md` for a second Compose project example. Stop writes to the source or use the snapshot as a point-in-time backup; later writes are not included.

To erase collected rows **only when intentionally starting over**, run `./scripts/reset-database.sh` and type `ERASE`; `--yes` bypasses that prompt. This truncates `aircraft_observations`, `collection_runs`, `flight_movements`, `wind_observations`, and `taf_forecasts`, resets IDs, and preserves the schema. Migration 003 must exist before this script runs.

## Verification and known gaps

Run `pytest` and `ruff check .` after code changes. Tests distinguish intentionally broad observation storage from narrower movement qualification, including an end-to-end collection-to-movement check. The former expected-failure test for 19 runway-threshold inclusion was removed because threshold inclusion is not a corridor requirement. The continuous runner provides best-effort local scheduling but no installed service. No rate-limit/backoff worker, full flight-leg correlation, origin/destination provider, validated statistics pipeline beyond the page's movement aggregations, broader public API, or deployment configuration exists yet. The bounded repeat runner is not a scheduler or rate-limit/backoff mechanism. Do not describe those planned capabilities as operational.

Before using collected counts publicly, confirm the intended polygon vertices and validate the approach-movement heuristic against real trajectories. Develop an evidence-based method for identifying landings (a single position, heading, and speed are insufficient), then address collection cadence, API limits, data retention/backups, licensing/attribution, and public-site privacy/security.
